# Enrollment and account binding

## Implemented local registration

After the existing MediaPipe exactly-one-face, framing, neutral pose and movement checks, the exact validated JPEG is processed by face-api.js. Tiny Face Detector checks it again, the tiny 68-point landmark model aligns the detected face, and the pretrained recognition network produces a 128-dimensional descriptor. This descriptor is not a MediaPipe landmark vector. Recognition weights are public assets served from this application; no photo or descriptor is uploaded.

The user separately consents to persistent template storage. Usernames are case-insensitive ASCII names (3–32 letters, numbers or underscores). IndexedDB stores an AES-256-GCM encrypted descriptor, a fresh 96-bit IV, a non-extractable per-record CryptoKey, model/schema identifiers, username, display name and creation time. Schema, model and username are authenticated as additional data. The template retains the model's original descriptor scaling; future comparison thresholds must be evaluated against this exact model.

An atomic IndexedDB `add` rejects existing usernames, including races across tabs. Deleting the record also deletes its encryption key. Successful registration discards the photo. Clear site data to delete all enrollment records. Templates are scoped to browser profile and origin; changing hostname/port creates a different storage scope. The UI can find and delete an existing enrollment after reload by entering the same username in Register.

Encryption reduces accidental disclosure from serialized template data. The key is stored beside the ciphertext because this is a browser-local prototype. Same-origin JavaScript, XSS, a compromised browser/profile, or a device administrator can access and decrypt templates. This is not hardware-backed biometric storage and does not provide an account authentication factor. Avoid third-party scripts; use HTTPS in deployment, strict CSP, dependency review, and evaluate storage/retention requirements before production.

## Decision for secure server binding (protocol design; not implemented)

Do not claim a server account or bind a template using only a username, a public key generated by JavaScript, an unsigned descriptor hash, or `livenessPassed: true`. A username in local IndexedDB establishes no server account ownership. No new registration endpoint is exposed in this milestone; FastAPI still serves only health.

Use a verified account bootstrap (a single-use signup invitation/email verification, or an already authenticated account) and a WebAuthn passkey with required user verification as the enrollment authorization credential. Enrollment does not establish civil identity; identity proofing would be a separate process if required.

1. Establish the account and register its passkey using a maintained WebAuthn server library. Verify the ceremony type, origin, RP ID hash, challenge, public key algorithm and user-verification flags. The server derives the account ID from the authenticated session, never from an arbitrary client username.
2. Locally create a versioned template and a random 32-byte secret blinding value. Define a canonical encoding for the quantized descriptor, model hash, schema and account ID before selecting the future proof circuit. Use a hiding commitment compatible with that circuit. An unblinded embedding hash is not a privacy-preserving commitment. Commitment code is deliberately deferred until the quantization and proof scheme are fixed.
3. Request an enrollment challenge over an authenticated, CSRF-protected session. Store a cryptographically random, short-lived nonce and the exact proposed commitment, account ID, credential ID, model/circuit versions and operation (`enroll`) in a pending server record. Rate-limit requests. Existing commitments cannot be replaced without fresh account authorization.
4. Require a fresh WebAuthn assertion against that pending challenge, with user verification. Verify the full assertion using the stored credential and the approved origin/RP ID. Atomically consume the challenge and persist the account-to-commitment binding. Reject expired, replayed, cross-account and wrong-operation challenges. Do not issue a login session based on local face checks.
5. For future face sign-in, prove knowledge of the enrolled template/blinding value and a match of a newly computed, version-compatible embedding within an evaluated threshold. Bind the proof to the account, enrolled commitment and a new single-use server nonce. The server verifies the actual proof and consumes the nonce atomically before issuing a session. Recovery and template rotation require the independent account credential and revoke the prior commitment.

A passkey assertion authorizes the enrollment commitment but does not attest that its contents came from a live camera or that this application performed face matching. A ZK proof over a client-supplied embedding likewise cannot establish camera provenance. Until trusted capture/spoof defenses are designed and evaluated, keep the passkey as the authoritative server authentication factor and treat browser face matching as a local convenience. Do not advertise face-only secure server authentication.
